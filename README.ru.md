**Nimbus Backup — клиент резервного копирования для Windows с открытым исходным кодом (GPL-3.0), работающий с Proxmox Backup Server (PBS).**
Современный графический интерфейс для резервного копирования серверов и рабочих станций Windows в PBS — согласованные снимки VSS, задания по расписанию, файловый и дисковый режимы, просмотр снимков и восстановление, поддержка нескольких серверов PBS и служба Windows, — а также инструменты командной строки для резервного копирования каталогов и целых машин. Нужно **внешнее (offsite), неизменяемое** хранилище PBS без собственного хостинга? См. [управляемый сервис](#️-управляемый-pbs-вне-площадки-и-неизменяемый) ниже.

Nimbus Backup — это сборка RDEM Systems проекта [Proxmox Backup Client GO](https://github.com/tizbac/proxmoxbackupclient_go): разработанный нами графический интерфейс был принят в upstream, и теперь оба проекта используют общую кодовую базу (см. [Связь с upstream](#-связь-с-upstream)).

## ✨ Возможности

### GUI (рекомендуется)
- **🌍 Многоязычность** — интерфейс на английском, французском, итальянском, немецком и польском языках
- Удобная настройка с проверкой подключения (токен API или имя пользователя/пароль)
- Ход резервного копирования в реальном времени со скоростью и оставшимся временем, отмена в любой момент
- Поддержка VSS (Volume Shadow Copy) для согласованных резервных копий
- Резервное копирование нескольких папок, файловый и дисковый (вся машина) режимы; папки могут обрабатываться параллельно (рекомендуется: число CPU / 4)
- Просмотр снимков, поиск файлов (с подстановочными знаками) и восстановление
- Поддержка нескольких серверов PBS, закрепление отпечатка сертификата (TOFU)
- **🔒 Шифрование на стороне клиента** (AES-256-GCM), файлы ключей совместимы с `proxmox-backup-client` и Proxmox VE
- Режим службы Windows + резервное копирование по расписанию, история резервных копий с повторным запуском в один клик
- Отладочное журналирование для диагностики

### Инструменты командной строки
- `proxmoxbackup-directory` — резервное копирование каталогов (PXAR) с дедупликацией, потоковое резервное копирование (`-backupstream`, например конвейер `mysqldump`), исключения (`-exclude "*.tmp"`, можно повторять, или `-exclude-from file`; `"exclude"` в JSON-конфигурации), несколько каталогов одновременно (`-parallel N`, рекомендуется: число CPU / 4), уведомления по электронной почте, файл конфигурации JSON
- `proxmoxbackup-machine` — полное резервное копирование работающей машины в виде загрузочного образа диска (FIDX): VSS в Windows, инкрементально, параллельное хеширование
- `proxmoxbackup-nbd` — NBD-сервер для монтирования дисковой резервной копии в Linux (восстановление на уровне файлов, восстановление на «голое железо» с [пропатченного live-ISO Clonezilla](PATCH-CLONEZILLA.md))

### Умные системные исключения (файловый режим)
При резервном копировании целого диска (например, `D:\`) Nimbus Backup автоматически исключает:

**Системные папки:** `System Volume Information` (хранилище VSS, может занимать 100+ ГБ), `$RECYCLE.BIN`, `Recovery`.
**Системные файлы:** `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`.

**Почему это важно:** диск может показывать 1,03 ТБ занятого места, тогда как реальные файлы занимают ~141 ГБ. Без исключений резервная копия включала бы снимки VSS (впустую потраченные место и время); с исключениями размер резервной копии соответствует реальным данным.

**Рекомендация:** используйте **файловый режим** (по умолчанию) с автоматическими исключениями для резервного копирования на уровне файлов; используйте **дисковый режим** в отдельном задании для восстановления на «голое железо» (включает всё).

### 🔒 Шифрование на стороне клиента
Резервные копии могут шифроваться **на клиенте** ещё до того, как покинут машину,
по той же схеме, что и в официальном `proxmox-backup-client` (AES-256-GCM, дайджесты
фрагментов с ключом). Сервер PBS хранит только непрозрачные данные и никогда не видит
ключ — это полезно на общем или управляемом PBS.

Шифрование разработано в исходном проекте Тициано Бакокко (Tiziano Bacocco, [tizbac/proxmoxbackupclient_go](https://github.com/tizbac/proxmoxbackupclient_go)); бумажная копия ключа, экспорт в QR-код и импорт ключа — дополнения Nimbus Backup.

- **GUI**: *Серверы → Изменить → Ключ шифрования* — создайте файл ключа или выберите
  существующий (созданный `proxmox-backup-client key create --kdf none` или из хранилища
  PVE); отображается его отпечаток. Затем сохраните копию вне машины:
  **Печать (бумажный ключ)** сохраняет страницу для печати с ключом и его QR-кодом (в
  формате `proxmox-backup-client key paperkey`), по желанию защищённую парольной фразой.
  **Импорт ключа из текста или QR-кода** превращает отсканированный QR-код или бумажный ключ
  обратно в файл ключа. GUI использует только незащищённые файлы ключей: при импорте
  ключа, защищённого парольной фразой, он разблокируется, и новый файл ключа сохраняется **без**
  парольной фразы — храните этот файл так же надёжно, как сам ключ.
- **CLI**: `-keyfile path/to/key.json` (или `"keyfile"` в JSON-конфигурации); для
  ключа, защищённого парольной фразой, используется `-keyfile-passphrase`, иначе она будет запрошена.
- **Восстановление на «голое железо»**: пропатченный ISO Clonezilla восстанавливает и зашифрованные
  дисковые резервные копии (ключ с USB-накопителя, с его парольной фразой, если она есть) — см.
  [PATCH-CLONEZILLA.md](PATCH-CLONEZILLA.md).
- **Совместимость с `proxmox-backup-client`, проверяемая в CI при каждой сборке**
  на реальном PBS: папка, зашифрованная Nimbus Backup ключом, созданным
  `proxmox-backup-client`, восстанавливается официальным клиентом с тем же ключом
  (и не восстанавливается без него), а зашифрованная дисковая резервная копия, созданная официальным
  клиентом, читается Nimbus Backup. Proxmox VE использует те же файлы ключей.

> ⚠️ **Без ключа зашифрованные резервные копии невозможно восстановить.** Первая
> зашифрованная резервная копия загружает всё заново (нет дедупликации с незашифрованными
> резервными копиями). Идентификаторы резервных копий, имена архивов и размеры остаются видимы серверу; содержимое
> файлов, имена файлов и каталог зашифрованы.

## 🤖 Автоматическое развёртывание (Ansible и IaC)

Nimbus Backup полностью устанавливается и настраивается из файлов — без интерактивной настройки.
Два пути, оба покрыты готовыми примерами в
[`examples/automation/`](examples/automation/):

- **Командная строка** — один JSON-файл на хост описывает всё резервное копирование
  (`proxmoxbackup-directory.exe --config file.json`); расписание — через Планировщик заданий
  Windows. Надёжные коды возврата (`0` OK, `1` фатальная ошибка, `2` заблокировано, `3` частично),
  чтобы ваш оркестратор обнаруживал сбои. Лучший вариант для чистой инфраструктуры как кода.
- **GUI/служба (MSI)** — **единственный `config.json`** содержит подключение к PBS,
  параметры резервного копирования **и** расписание (`scheduled_jobs`). Разместите файл, перезапустите
  службу `NimbusBackup`: задания согласуются идемпотентно, а `nextRun`
  вычисляется автоматически. Никаких вычислений меток времени в вашем шаблоне Jinja2.

Служба читает конфигурацию из `C:\ProgramData\ProxmoxBackupClient\`
(начиная с 0.4.0; см. [Обновление](#️-обновление-с-версий--030)).

📖 Полное пошаговое руководство: [Автоматизация резервного копирования Windows в PBS с Ansible](https://nimbus.rdem-systems.com/en/blog/unattended-windows-backup-ansible/?utm_source=github).

## 🚀 Быстрый старт

1. Скачайте `NimbusBackup.msi` (или автономный `NimbusBackup.exe`) со страницы релизов
2. Установите / запустите его с правами администратора (требуется для VSS)
3. Настройте подключение к PBS и проверьте его
4. Выберите каталоги для резервного копирования
5. Запустите резервное копирование — или запланируйте его

### 🔑 Пользователь PBS и права доступа

Клиенту нужна только роль **`DatastoreBackup`** на целевом хранилище данных — учётная запись администратора не требуется:

1. В веб-интерфейсе PBS создайте пользователя (например, `nimbus@pbs`) и токен API для него (например, `nimbus@pbs!laptop01`).
2. В разделе **Datastore → Permissions** (или **Configuration → Access Control → Permissions**) назначьте `DatastoreBackup` на `/datastore/<name>` — или на `/datastore/<name>/<namespace>`, если вы делаете резервные копии в пространство имён.
3. **Токен с разделением привилегий** (флажок «Privilege Separation» установлен, по умолчанию): назначьте роль самому **токену** (`nimbus@pbs!laptop01`), а не только пользователю — эффективные права являются пересечением обоих. Это самая частая причина ошибки «permission denied».

`DatastoreBackup` позволяет клиенту создавать резервные копии, а также просматривать и восстанавливать собственные группы резервных копий. Для удаления или очистки (prune) снимков нужна роль `DatastorePowerUser`.

## ⬆️ Обновление с версий ≤ 0.3.0

Установка 0.4.0 или более поздней версии поверх существующей обновляет её на месте (та же идентичность MSI, та же служба `NimbusBackup`). Папка данных переносится из `C:\ProgramData\NimbusBackup` в общую `C:\ProgramData\ProxmoxBackupClient`: при первом запуске ваша конфигурация, задания по расписанию, история и токен API копируются один раз (существующие файлы никогда не перезаписываются). Старая папка сохраняется и помечается файлом `COPIED-TO-ProxmoxBackupClient.txt`, поэтому откат на старую версию по-прежнему возможен. Снимки, созданные старыми версиями, по-прежнему можно восстановить в исходное расположение.

Бренд выбирается по имени исполняемого файла: `NimbusBackup.exe` работает как Nimbus Backup, с любым другим именем — как нейтральный «Proxmox Backup Client» ([`gui/brand.go`](gui/brand.go)).

## 🔗 Связь с upstream

Nimbus Backup начинался как форк [tizbac/proxmoxbackupclient_go](https://github.com/tizbac/proxmoxbackupclient_go) (Proxmox Backup Client на Go, автор Tiziano Bacocco, GPLv3), к которому мы добавили GUI для Windows, службу, планирование, поддержку нескольких PBS и восстановление. В сентябре 2026 года upstream принял этот GUI обратно и сделал его брендонейтральным («Proxmox Backup Client GUI»). Начиная с 0.4.0, Nimbus Backup собирается из той же кодовой базы: **функционально оба проекта теперь практически идентичны.**

Поверх upstream этот репозиторий добавляет небольшую документированную серию патчей ([`patches/`](patches/README.md)):

- **Исправления, ещё не принятые в upstream** (сборка службы, восстановление с серверов с именем пользователя/паролем, коды возврата, скрытие данных в журналах, надёжность резервного копирования машин…) — отправляются в upstream и принимаются там постепенно.
- **Идентичность Nimbus Backup** — `NimbusBackup.exe`/`.msi`, служба `NimbusBackup` и код обновления (upgrade code) MSI существующих установок, чтобы они продолжали обновляться на месте.
- **Путь обновления** с Nimbus Backup ≤ 0.3.0 (перенос папки данных, устаревшие метаданные снимков).
- **Конвейер выпуска релизов** — аттестация происхождения сборки, контрольные суммы, отчёты VirusTotal.

Мы регулярно заново сливаемся с upstream; собственные релизы upstream публикуются в [tizbac/proxmoxbackupclient_go](https://github.com/tizbac/proxmoxbackupclient_go/releases).
